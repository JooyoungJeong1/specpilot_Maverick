# 요구사항 단위 형식
단위 하나는 아래 필드를 모두 가진다. 값이 없으면 null 또는 빈 배열로 둔다.

- key: 이 응답 안에서만 쓰는 번호. 화면 단위는 "u01", "u02"…, 앱 전체 단위는 "a01", "a02"…. 설계서에 나오는 순서대로 매기고 함의 단위는 맨 뒤에 둔다. 최종 단위 ID(REQ-…)는 프로그램이 붙이므로 쓰지 않는다.
- screen_id: 화면 ID. 앱 전체 단위는 "APP".
- source: 근거 위치 목록. 예) ["Description 2-(1)", "Action E"], ["상태 화면 p.2"], ["화면 이미지"]. 함의 단위는 근거가 된 위치를 모두 적고, 다른 화면이면 화면 ID를 붙인다. 예) ["LOGIN-004 Description 0", "Action A"]
- quote: 근거 원문을 짧게 잘라 고치지 않고 그대로 옮긴다. 오타도 그대로 두고, 중간을 줄이지 않는다(이어진 부분만 자른다). 프로그램이 원문과 대조한다. 함의 단위는 근거 원문들을 " / "로 잇는다.
- origin: "명시" 또는 "함의"
- reason: 함의 단위만 "A이고 B이므로 C" 한 문장. 명시 단위는 null.
- kind: 아래 여덟 가지 중 하나
  - 표시: 화면 진입이나 특정 상태에서 무엇이 어떻게 보이는가 (구성, 형식, 순서, 가림 표시)
  - 검증: 서버 확인 없이 입력값을 검사한 결과 (형식, 길이, 필수, 일치, 날짜 순서)
  - 상태: 요소의 상태가 바뀜 (버튼 활성화, 토글, 선택 강조)
  - 이동: 화면 이동, 새 창, 팝업·알림창이 열리고 닫힘
  - 처리: 저장·수정·삭제·집계처럼 데이터가 바뀌거나 반영되는 결과
  - 실패: 서버 확인 뒤 실패했을 때의 안내 (이미 가입된 이메일, 로그인 정보 불일치)
  - 접근: 로그인 여부나 역할에 따라 보이거나 쓸 수 있는 범위
  - 제약: 화면 결과로 바꿔 쓸 수 없는 처리 방식만 (예: 서버 확인 없이 검사한다). 화면에서 보이는 결과로 바꿀 수 있으면(예: "삭제할 수 없다" → 삭제하기 버튼이 보이지 않는다) 제약이 아니라 그 결과의 kind로 만든다. 제약으로 두면 issue에 "결과로 바꿀 수 없는 이유"를 한 문장 적는다. 사양서에는 쓰지 않고 정합성 판정에만 쓴다.
- given: 사전 상태 (로그인 여부, 역할, 앞선 조작). 없으면 null.
- when: 사용자 행동 또는 시점. 화면에 보이는 라벨로 쓴다. 마커가 붙은 요소가 대상이면 그 요소의 라벨을 쓴다.
- conditions: 결과가 나오려면 함께 만족해야 하는 조건 목록(AND).
- then: 관찰할 수 있는 결과 하나.
- exact: 설계서 원문 값만 넣는다.
  - message: 원문 문구 (error-msg·msg·따옴표 안 문장) 또는 null. 글자는 설계서 그대로 옮긴다. 띄어쓰기는 비교하지 않으므로 맞추지 않아도 된다. 텍스트와 이미지의 글자가 서로 다르면 텍스트를 쓰고 issue에 적는다. 설계서에 문구가 없으면 지어내지 않고 null로 둔다.
  - values: 원문의 수치·형식·선택지·표시법 목록
  - target: 이동하거나 열리는 화면의 ID(없으면 이름) 또는 null
- issue: 이 단위 안에서 불분명한 점 (값 미명시, 모순, 잘린 문장, 명칭 차이, 이미지로 확인되지 않음). 없으면 null.
- ref_hint: 값이 이 화면에 없는데 다른 화면에 같은 규칙으로 보이는 값이 적혀 있을 때만 {"screen_id": 그 화면 ID, "source": 그 위치, "value": 그 값}. 이 값은 exact에 넣지 않는다. 이 화면에서 값이 비어 있다는 사실은 issue에 적는다. 없으면 null.

# 확인 질문 형식
- key: "q01", "q02"…. 이 응답 안에서만 쓰는 번호. 최종 질문 ID(Q-…)는 프로그램이 붙인다.
- topic: 짧은 주제
- question: 기획자에게 묻는 문장
- why: 왜 묻는지. 설계서 근거가 있으면 위치와 함께 적는다.
- priority: "상" 또는 "하". 상: 이름 없는 역할, 서로 맞지 않는 두 서술처럼 설계서 안에서 결과를 정할 수 없는 것. 하: 설계서 근거 없이 보통 그렇다는 관행으로만 떠오른 것.
- related_units: 관련 단위 key 목록 (이 응답 안의 key. 없으면 빈 배열)

# 문장 규칙
- given, when, then은 화면에 보이는 라벨로 쓰고 코드·아키텍처 용어(API, 함수, 테이블, 컴포넌트)를 쓰지 않는다. kind가 "제약"이면 설계서 표현 그대로 쓴다.
- 오타(글자 하나 틀림, 띄어쓰기 어긋남)는 문맥상 뜻이 하나로 정해지면 바른 뜻으로 읽고 넘어간다. 이런 오타는 issue나 질문으로 만들지 않는다. quote에는 원문 그대로 두고, given·when·conditions·then에서는 바로잡아 쓴다.
- exact(문구, 라벨, 값)는 코드와 글자를 대조하는 값이라 원문 글자를 그대로 쓴다. 그 안에 오타가 있으면 바로잡지 않고 issue에 "원문 오타로 보임: 바른 표기"를 적는다.
- 오타가 아니라 뜻이 달라지는 오류(이 화면에 없는 입력란 이름, 다른 화면의 문구가 남은 서술, 부정·숫자·대상이 바뀐 것)는 바로잡지 않고 issue에 적는다.
