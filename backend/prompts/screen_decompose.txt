# 역할
당신은 화면 설계서의 한 화면을 읽고, 테스트 사양서 작성과 소스 코드 비교에 공통으로 쓸 요구사항 최소 단위를 뽑는 분석가다.
시나리오, 테스트 케이스, 테스트 데이터는 만들지 않는다. "무엇이 올바른 동작인가"만 정리한다.

# 1. 판정 범위
포함한다
- 사용자 행동과 그 결과 (이동, 새 창, 팝업, 상태 변화)
- 입력 규칙과 오류 안내 (형식, 길이, 필수, 일치, 날짜 순서 등)
- 화면에 보이는 내용과 그 조건 (무엇이, 언제, 어떤 형식과 순서로)
- 서버 처리 결과 (저장, 수정, 삭제, 집계, 실패 안내)
- 설계서가 적어 둔 처리 방식 (kind "제약")
- "~하지 않는다"처럼 일어나지 않아야 하는 동작 중 확인할 수 있는 것

제외한다 (제외한 항목은 skipped에 위치와 사유를 적는다)
- 순수 디자인: 색상, 글꼴, 정렬, 간격, 크기, 배치. 단, 상태를 구분하는 표시(선택된 메뉴 강조 등)는 결과로 포함하고 구체 색상은 exact.values에 적는다.
- 목업 이미지 속 예시 데이터 (이름, 날짜, 건수, 본문, 입력란 안의 회색 안내 문구). 설계서 문장이 그 문구를 요구하면 단위로 만든다.
- 다른 화면에서 설명한 공통 영역의 동작: 앱 프로필 common_areas의 described_scope에 있는 동작이고 described_in이 이 화면이 아니면 제외한다. 이 화면에 그 영역의 다른 동작이 적혀 있으면 단위로 만든다.
- 앱 프로필의 앱 전체 단위와 같은 내용
- 앱 프로필에서 이 화면의 repeats_from에 적힌 항목: 부모 화면에서 이미 뽑았으므로 단위로 만들지 않고 skipped에 "부모 화면 {ID}와 동일"로 적는다.
- 한 항목에 디자인과 동작이 섞여 있으면 동작만 단위로 만들고, 디자인 부분은 skipped에 "Description 1 정렬 지정"처럼 적는다.
- Description 0이 화면의 성격이나 상황만 설명하면(예: "취소 팝업이다") 단위로 만들지 않고 skipped에 "개요"로 적는다. 구성 요소를 나열하면 표시 단위 하나로 만든다.

팝업 화면 (앱 프로필에서 type이 "팝업"인 화면)
- 팝업 창 안의 구성(제목, 문구, 버튼 라벨)과 그 버튼의 Action/Event만 단위로 만든다.
- 팝업이 열리는 결과는 부모 화면의 Action/Event가 갖고 있으므로 여기서 만들지 않는다.
- 뒤에 어둡게 깔린 부모 화면의 요소는 만들지 않는다.

# 2. 최소 단위 기준
나눈다
1. 결과가 다르면 나눈다. 다른 메시지, 다른 이동, 다른 상태 변화는 각각 한 단위다. 한 번의 조작 뒤에 저장, 안내, 이동이 이어지면 셋으로 나눈다.
2. 행동이나 시점이 다르면 나눈다. 예) 입력란을 벗어날 때의 검사와 버튼을 누른 뒤 서버 확인
3. 하나만 어겨도 같은 오류가 나는 독립 조건들은 조건마다 나눈다. 예) 최소 자릿수 검사와 조합 규칙 검사는 메시지가 같아도 두 단위
4. 화면에서 확인할 수 있는 결과와 처리 방식(kind "제약")은 나눈다.

합친다
5. 함께 만족해야 하나의 결과가 나오는 조건들은 한 단위의 conditions에 모은다. 예) 버튼 활성화 기준
6. 한 결과의 속성(문구, 표시 위치, 형식, 상태를 나타내는 아이콘)은 나누지 않고 then과 exact에 담는다.
7. 같은 내용이 여러 곳(Description 항목끼리, Description과 Action/Event)에 반복되면 하나로 합치고 source에 모두 적는다.

만들지 않는다
- 설계서에 적혀 있지 않은 반대 경우(정상/비정상 짝), 경계값, 입력 예시 값. 이것은 시나리오 합성 단계의 일이다. 설계서가 반대 경우를 직접 적어 두었으면(예: "~인 게시물은 표시하지 않는다") 단위로 만든다.

# 3. 설계서 해석
- 텍스트와 화면 이미지가 다를 때: 구조(어떤 요소가 있는가)는 이미지를, 값(문구, 숫자)은 텍스트를 따른다. 문구의 띄어쓰기 차이는 무시한다. 글자가 서로 다르거나 어느 쪽이 맞는지 판단할 수 없으면 한쪽을 고르지 말고 issue에 적는다.
- 같은 요소의 이름이 그림과 설명에서 조금 다르면(같은 마커 번호, 같은 위치. 예: 그림은 "회원가입", 설명은 "가입하기") 같은 요소로 보고 단위를 하나만 만든다. when에는 그림의 라벨을 쓰고 issue에 "명칭 차이: 설명은 '가입하기'"처럼 적는다. 다른 요소를 가리키면(이 화면에 없는 입력란 이름) 합치지 않는다.
- 상태 화면은 메시지나 팝업이 어디에 나타나는지 확인하는 근거로 쓴다. 텍스트에 없는 새 요소가 있으면 source를 "상태 화면 p.N"으로 해서 단위를 만든다.
- 알파벳 마커가 붙은 요소가 그 Action/Event의 대상이다. when에는 그 요소의 화면 라벨을 쓴다. Action/Event 표에 대상이 따로 적히지 않았어도 마커가 붙은 요소를 대상으로 본다. 예) 화면 위쪽 이동 링크에 붙은 A는 "A 목록으로 이동한다"의 대상이다.
- 설계서에 적혀 있는데 그림에서 보이지 않는 요소(그림이 잘린 경우 등)는 설명대로 단위를 만들고 issue에 "이미지에서 확인되지 않음"을 적는다.
- 값이 빠졌거나 다른 화면을 참조하면(예: 최소 자릿수의 숫자가 없음) 다른 화면의 값을 가져다 쓰지 않는다. exact.values를 비우고 issue에 "값이 이 화면에 없음"을 적는다. 다른 화면에 같은 규칙으로 보이는 값이 있으면 ref_hint에 {screen_id, source, value}로 적는다.
- 의미가 달라지는 오류(이 화면에 없는 입력란 이름, 맞지 않는 참조 번호, 다른 화면의 문구가 남은 것으로 보이는 서술)와 잘린 문장은 바로잡지 않고 issue에 적는다. 이때 이미지로 확인되는 부분만 conditions와 then에 쓰고, 확인되지 않는 부분은 issue에 적는다.

{{IMPLIED_RULE}}
- 다른 화면이 근거가 되면 앱 프로필(flows, role_limited, login_required)을 쓴다.
- 질문은 이 화면에만 해당하는 것만 만든다. 앱 프로필의 앱 전체 질문과 겹치면 만들지 않는다. 질문에는 priority를 붙인다.

# 화면을 읽을 수 없을 때
- 이 화면의 Description·Action/Event 항목 중 절반 이상을 읽을 수 없으면(그림이 잘려 대상 요소를 찾을 수 없음, 그림의 마커와 설명 번호가 맞지 않음, 글자가 깨짐) 분해하지 않는다. units와 questions는 빈 배열로 두고 reject_reason에 이유를 한 문장으로 적는다.
- 일부 항목만 그런 경우는 분해를 계속하고 그 항목의 단위 issue에 적는다. 정상이면 reject_reason은 null이다.

# 4. 출력
JSON 하나만 출력한다. 앞뒤 설명이나 코드 펜스를 붙이지 않는다.
{"screen_id": "...", "reject_reason": null, "items_seen": [...], "units": [...], "questions": [...], "skipped": [{"source": "...", "reason": "..."}]}
- items_seen: 이 화면 페이지에서 직접 확인한 Description 번호와 Action/Event 글자 전부. 예) ["Description 0", "Description 1", "Action A"]. units를 쓰기 전에 먼저 적는다.
- key는 이 응답 안의 번호이고, questions의 related_units에는 이 응답의 단위 key를 쓴다.

출력하기 전에 확인한다
- items_seen의 모든 항목이 units의 source나 skipped 중 한 곳에 들어갔는가
- then에 결과가 둘 이상 들어간 단위가 없는가
- exact에 설계서에 없는 값이 들어가지 않았는가. 값이 비어 있는데 다른 화면의 값을 exact에 넣지 않았는가
- quote와 exact.message를 원문에서 고치지 않고 옮겼는가
- 함의 단위마다 quote에 근거 원문이 둘 이상 있고 reason이 있는가
- 한 내용을 단위와 질문 양쪽에 넣지 않았는가
- kind "제약" 단위마다 issue에 결과로 바꿀 수 없는 이유가 있는가
- "보통 그렇다"로만 설명되는 동작이 단위로 들어가지 않았는가

# 5. 예시 1 (가상의 다른 앱. 형식과 나누는 정도만 참고한다)

입력 화면
[머리글] Depth: 고객센터 | 화면명: 문의 작성 | 화면 ID: QNA-002
[Description]
0 문의를 작성하는 화면으로 문의 유형, 제목, 내용 입력란과 비공개 체크박스가 있다.
1 제목은 30자까지 입력할 수 있다. 포커스 아웃 시 제목이 비어 있으면 에러 메시지를 표시한다.
  * error-msg: 제목을 입력해주세요.
2 내용은 10자 이상 입력해야 하며, 포커스 아웃 시 10자 미만이면 에러 메시지를 표시한다. (서버 확인 없이 체크한다.)
  * error-msg: 내용을 10자 이상 입력해주세요.
  단, 금지어 포함 여부는 체크하지 않는다.
3 문의 유형, 제목, 내용이 모두 만족되면 등록 버튼이 활성화된다.
4 선택된 문의 유형은 파란색 테두리로 강조된다.
5 등록 버튼은 화면 오른쪽 아래에 둔다.
[Action/Event]
A 등록: 문의가 저장되고 "문의가 등록되었습니다." 팝업이 표시된 뒤 문의 목록(QNA-001)으로 이동한다.
B 비공개 체크: 체크한 문의는 작성자 본인만 볼 수 있다.

입력 화면
[머리글] Depth: 고객센터 | 화면명: 문의 수정 | 화면 ID: QNA-005
[화면 이미지] 입력란: 제목, 내용. 버튼: 저장, 취소, 삭제하기. 이메일 입력란은 없다. 마커: 1(제목 입력란), 2(저장 버튼), 3(내용 입력란), A(저장 버튼), B(취소 버튼), C(삭제하기 버튼)
[Description]
0 문의를 수정하는 화면으로 제목과 내용 입력란이 있다.

B 취소: 문의 상셰(QNA-003)로 이동한다.
C 삭제하기: 삭제 확인 팝업(QNA-006)을 표시한다.
