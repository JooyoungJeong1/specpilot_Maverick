# 프롬프트 v3.1 → 백엔드 반영본: 바꾼 곳

`specpilot-prompts-v3.1.md`를 `prompts/` 폴더로 옮기면서 바꾼 곳만 적는다. 여기 없는 문장은 v3.1 그대로다.
프롬프트를 더 고칠 때는 `prompts/`의 파일을 직접 고친다 (코드는 `{{자리표시자}}`만 채운다).

## 왜 바꿨나

- **띄어쓰기**: v3.1은 "추출 텍스트에 띄어쓰기가 빠진다"는 전제로 문구를 이미지에서 읽게 했다. 이 누락은 pypdf로 뽑을 때 생기는 것이고, pdftotext로 읽으면 원문 띄어쓰기가 남는다 (ver0.2 기준 한글 사이 공백 pdftotext 1,545곳, pypdf 70곳). 원문 자체도 "확인해주세요"(5곳)와 "확인해 주세요"(2곳)가 섞여 있다. 그래서 띄어쓰기는 아예 비교하지 않기로 했다. 프로그램의 원문 대조와 ③ 판정이 모두 띄어쓰기를 무시하고, ②는 글자만 정확히 옮긴다.
- **함의·질문 이중 생성**: v3.1은 근거가 약하면 "단위 + 확신 낮음 + 같은 내용의 질문"을 함께 만들게 했다. 실행 점검에서 4쌍(a02↔q05, a04↔q06, a05·a06↔q07, a11↔q03)이 이렇게 나왔고, 근거가 약한 가정이 요구사항처럼 ③ 판정과 ④ 사양서로 흘러간다. 근거가 약하면 **질문만** 만들게 바꿨다. 함의를 질문으로 내리는 쪽은 사람이 질문 목록에서 보고 고치지만, 질문이 함의로 올라가는 쪽은 조용히 퍼지기 때문이다.
- **오타**: 문맥상 뜻이 하나로 정해지는 오타(글자 하나, 띄어쓰기)는 바른 뜻으로 읽고 넘어간다. issue나 질문을 만들지 않는다. 단 quote는 원문 그대로 두고, 코드와 글자를 대조하는 값(exact)은 원문 글자를 유지하고 issue에 적는다.
- **읽을 수 없는 화면**: 항목의 절반 이상을 읽을 수 없으면 ②가 분해하지 않고 `reject_reason`을 낸다. ①은 보이는 문제를 `reading_notes`에 적기만 한다. 반려 판단은 프로그램(입력 점검, 게이트)이 먼저 하고, ②의 반려는 그 뒤의 안전장치다.

## 공통 블록 (`prompts/blocks/`)

- `reading_guide.txt`
  - 띄어쓰기 줄: "문구의 글자와 띄어쓰기는 페이지 이미지에서 확인한다" → "띄어쓰기는 다음 단계에서 비교하지 않으므로 맞추려고 하지 않는다. 문구는 글자만 정확히 옮긴다"
- `implied_rule.txt`
  - 판단 질문에 "그 문장은 이 동작을 직접 다루는가?"를 덧붙임 (실행 점검 N8. "바꾼 비밀번호로 로그인된다" 같은 관행형 함의를 줄이려고)
  - 함의 단위의 quote는 근거 원문 **둘 이상**을 " / "로 잇는다
  - 지어내지 않는 것의 예시 추가: 설계서에 없는 문구, 버튼 활성화 조건, 빈 목록이나 오류일 때의 표시
  - "근거가 약하거나 서로 맞지 않으면 단위를 만들고 확신 낮음 + 같은 내용을 질문으로도" → "단위를 만들지 않고 질문만. 한 내용은 단위와 질문 중 한 곳에만"
- `unit_schema.txt`
  - quote: 고치지 않고, 중간을 줄이지 않고, 이어진 부분을 그대로 옮긴다 (프로그램이 원문과 대조함을 명시)
  - exact.message: 이미지에서 읽기 → 설계서 글자를 그대로. 띄어쓰기는 맞추지 않아도 됨. 텍스트와 이미지의 글자가 다르면 텍스트 + issue. 문구가 없으면 지어내지 않고 null
  - issue 예시: "확신 낮음"을 빼고 "명칭 차이, 이미지로 확인되지 않음"을 넣음
  - 문장 규칙의 오타 규칙을 세 줄로 정리 (위 "오타")

## ① `prompts/app_profile.txt`

- 강도 규칙 둘째 줄: 한쪽 화면이 연결을 말하지 않으면 "단위 + 확신 낮음 + 질문" → "질문만"
- `screens.screen_id`: 설계서에 화면 ID가 없으면 지어내지 않고 null. 프로그램이 `SCR-001`… 을 붙이고 `id_assigned: true`로 표시한다
- `reading_notes` 추가: 그림 잘림, 마커와 번호 불일치, 화면 ID 없음, 글자 깨짐을 {screen_id, pages, note}로 적기만 한다
- 확인 질문 셋째 줄: "확신이 낮은 함의 단위와 같은 내용" → "근거가 약해 단위로 만들지 않은 화면 사이의 연결"

## ② `prompts/screen_decompose.txt`

- 3절 첫 줄: 문구의 띄어쓰기 차이는 무시. 글자가 다르거나 판단할 수 없으면 issue
- 3절 추가: **명칭 차이**. 그림과 설명에서 이름이 조금 다르면(같은 마커, 같은 위치) 단위 하나로, when은 그림의 라벨, issue에 "명칭 차이: 설명은 '…'". 다른 요소를 가리키면 합치지 않음
- 3절 추가: 설계서에 있는데 그림에서 보이지 않는 요소는 설명대로 단위를 만들고 issue에 "이미지에서 확인되지 않음"
- 새 절 **화면을 읽을 수 없을 때**: 항목 절반 이상을 못 읽으면 분해하지 않고 `reject_reason`. 일부만이면 계속하고 그 단위 issue에
- 출력 형식에 `reject_reason` 추가
- 출력 전 확인: "exact.message를 페이지 이미지에서 확인해 적었는가" → "quote와 exact.message를 원문에서 고치지 않고 옮겼는가". "함의 quote가 둘 이상인가", "한 내용을 단위와 질문 양쪽에 넣지 않았는가" 추가
- 입력: 원본 페이지 번호(`{{SCREEN_PAGES}}`)는 기존 백엔드대로 유지 (화면 페이지만 잘라 보내서 "상태 화면 p.N"의 N을 맞추려고)

## ③ `prompts/judge.txt`

- 문구는 띄어쓰기를 비교하지 않는다. 띄어쓰기만 다르면 구현 + note "띄어쓰기 차이"
- 단위 issue에 "원문 오타로 보임"이 있고 코드가 바른 표기와 같으면 불일치 + note "설계서 오타 의심"
- 단위 issue에 "명칭 차이"가 있으면 코드가 두 이름 중 하나와 같을 때 같은 것으로 본다
- ref_hint는 판정 기준으로 쓰지 않는다

## 프롬프트 대신 프로그램이 하는 것

v3.1 변경 문서 3장("프로그램이 해야 할 일")과 실행 점검 결과에서 나온 것.

- key(u01, a01, q01) → 최종 ID(REQ-…, Q-…) 부여, related_units의 key를 ID로 변환 (3장 1번. 재실행 때 ID를 이어받는 매칭은 아직 안 함)
- items_seen 세 군데 대조: 프로그램 체크리스트 / items_seen / units·skipped (3장 2번)
- quote와 exact.message 원문 대조: 원문에 없으면(지어낸 근거) 재시도, 한두 글자만 다르면(오타를 고쳐 씀) 경고 (실행 점검 N3)
- 함의 검사: 근거 원문 둘 이상, 원문에 실제로 있음, "확신 낮음" 표시 없음. 못 채우면 단위에서 빼서 질문으로 옮기고 원래 단위는 `draft_unit`에 보관. 같은 내용의 질문이 이미 있으면 새 질문을 만들지 않고 그 질문에 붙인다 (예상 문제 7번)
- 입력 점검에서 그림에 마커가 없던 항목의 단위에 issue 자동 표시 (예상 문제 2번)
- 질문은 priority 상을 먼저 (3장 5번)
- ③에서 띄어쓰기만 다른 문구 불일치는 구현으로 바꾸고 원래 판정을 남김 (3장 6번)
- 아직 안 함: 같은 규칙 단위 묶음 표시(3장 3번), 제약 단위 모음(3장 4번), 재실행 시 ID 승계(예상 문제 16번)
